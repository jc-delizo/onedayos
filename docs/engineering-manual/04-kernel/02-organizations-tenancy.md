# 1. Purpose

This document defines how **Organizations**, **tenancy**, **organization slugs**, **branches**, **departments**, and tenant route access work in OneDayOS.

This is one of the most important Kernel documents because OneDayOS is a shared platform for many businesses.

The system must make this impossible:

```txt
User from Company A guesses Company B's URL
→ loads Company B's app shell
→ reads or mutates Company B's data
```

The restarted OneDayOS build must treat tenant isolation as a **foundation**, not as a patch.

---

# 2. Core Decision

OneDayOS uses this tenancy model:

```txt
One PostgreSQL database
Shared tables
Every tenant-scoped row has orgId
Every authenticated platform user belongs to exactly one Organization in MVP
Every platform route is scoped by orgSlug
Every server operation derives orgId from verified PlatformContext
No client-supplied orgId is trusted
```

The Organization is the tenant boundary.

```txt
Organization = tenant = client company = security boundary
```

# 4. Definitions

## 4.1 Organization

An **Organization** is a customer company using OneDayOS.

Examples:

```txt
ABC Hardware Trading
Dela Cruz Dental Clinic
Northstar Logistics Corp
```

An Organization owns:

- users
- roles
- permissions
- branches
- departments
- enabled modules
- settings
- subscriptions
- business objects
- module records

An Organization is the top-level tenant scope.

---

## 4.2 Tenant

A **tenant** is the isolated data and application boundary for one Organization.

In OneDayOS MVP:

```txt
tenantId = orgId
```

The terms may be used interchangeably in discussion, but the code should prefer `orgId` because the database model is named `Organization`.

---

## 4.3 orgId

`orgId` is the internal database identifier for an Organization.

It must be:

- generated by the server
- stored on every tenant-scoped row
- used in database queries
- never accepted from the client as authority

The client should almost never need to know `orgId`.

---

## 4.4 orgSlug

`orgSlug` is the URL-safe public identifier for an Organization.

Example:

```txt
Organization name: ABC Hardware Trading
orgSlug: abc-hardware-trading
Route: /abc-hardware-trading/dashboard
```

`orgSlug` is a locator, not proof of access.

The server must always verify:

```txt
authenticated user
+ platform User record
+ organization exists
+ user.orgId === organization.id
```

---

## 4.5 Branch

A **Branch** is a physical or operational location under an Organization.

Examples:

```txt
Head Office
Makati Branch
Cebu Warehouse Office
North Luzon Sales Office
```

Branch belongs in the Kernel because many modules need location structure.

Examples:

- Employees can belong to a branch.
- Warehouses can optionally be associated with a branch.
- Inventory operations may be branch-aware.
- Reports may group by branch.
- Permissions may later be branch-scoped.

---

## 4.6 Department

A **Department** is an organizational unit under an Organization.

Examples:

```txt
Operations
Sales
Accounting
Human Resources
Warehouse Team
```

Departments may optionally belong to a Branch.

This supports both common SME structures:

```txt
Organization → Branch → Department
```

and simpler structures:

```txt
Organization → Department
```

---

## 4.7 PlatformContext

`PlatformContext` is the verified server-side context produced by the Kernel after authentication and tenant validation.

It is the only safe way for services and modules to know which tenant they are operating inside.

Module services should receive:

```ts
PlatformContext
```

not:

```ts
orgId: string
```

This prevents accidental use of client-supplied tenant IDs.

# 5. Tenancy Principles

## 5.1 Organization is the tenant boundary

Every protected application route belongs to exactly one Organization.

```txt
/[orgSlug]/dashboard
/[orgSlug]/employees
/[orgSlug]/inventory
/[orgSlug]/settings
```

There should be no tenant-ambiguous business routes such as:

```txt
/dashboard
/inventory
/employees
```

Exception:

```txt
/login
/register
/api/kernel/auth/*
```

These exist before tenant context is available.

---

## 5.2 orgSlug is not authorization

A valid URL does not imply access.

Bad thinking:

```txt
The route contains /abc-corp, so load ABC Corp.
```

Correct thinking:

```txt
The route contains /abc-corp.
Find that org.
Find the authenticated platform user.
Verify user.orgId equals org.id.
Only then create PlatformContext.
```

---

## 5.3 orgId must be derived server-side

The client must not send authoritative `orgId` values.

Forbidden API pattern:

```txt
GET /api/inventory/products?orgId=org_abc
POST /api/employees { orgId: "org_abc", name: "Juan" }
```

Required API pattern:

```txt
GET /api/orgs/[orgSlug]/inventory/products
POST /api/orgs/[orgSlug]/employees { name: "Juan" }
```

The server derives `orgId` from:

```txt
session user
+ platform User record
+ orgSlug route param
+ membership check
```

---

## 5.4 Every tenant-scoped query must include orgId

Any table that belongs to a customer Organization must be queried with `ctx.orgId`.

Required:

```ts
await db.employee.findMany({
  where: {
    orgId: ctx.orgId,
    deletedAt: null,
  },
})
```

Forbidden:

```ts
await db.employee.findMany()
```

Forbidden:

```ts
await db.employee.findUnique({
  where: { id: employeeId },
})
```

The second pattern is dangerous because an attacker could pass an ID from another Organization.

Preferred pattern:

```ts
await db.employee.findFirst({
  where: {
    id: employeeId,
    orgId: ctx.orgId,
    deletedAt: null,
  },
})
```

---

## 5.5 Every tenant-scoped create must set orgId from context

Required:

```ts
await db.employee.create({
  data: {
    orgId: ctx.orgId,
    name: input.name,
  },
})
```

Forbidden:

```ts
await db.employee.create({
  data: {
    orgId: input.orgId,
    name: input.name,
  },
})
```

---

## 5.6 Related records must be tenant-validated

If a request includes a relation ID, the server must verify that relation belongs to the same Organization.

Example:

```ts
if (input.branchId) {
  const branch = await db.branch.findFirst({
    where: {
      id: input.branchId,
      orgId: ctx.orgId,
      deletedAt: null,
    },
  })

  if (!branch) {
    throw new ValidationError('Invalid branch.')
  }
}
```

Never assume a relation ID is safe just because the current user is authenticated.

---

## 5.7 Tenant isolation is enforced before permissions

The correct order is:

```txt
1. Authenticate user
2. Resolve platform User record
3. Resolve Organization by orgSlug
4. Verify user belongs to Organization
5. Verify Organization is active
6. Verify subscription/module status
7. Verify permissions
8. Execute operation
```

Permission checks should never run against a tenant the user does not belong to.

# 6. MVP User Membership Decision

## 6.1 Decision

For the MVP/new build, OneDayOS uses a **single-organization user model**:

```txt
User.orgId → Organization.id
```

A platform user belongs to exactly one Organization.

This is deliberate.

---

## 6.2 Why not multi-org membership now?

A more flexible model would use:

```txt
User
OrganizationMembership
Organization
```

That model is eventually useful for:

- consultants managing multiple clients
- OneDayOS internal support users
- accountants working across multiple companies
- franchise-style organizations
- external agencies

However, for the initial OneDayOS market, the simpler model is better.

Reasons:

1. Philippine SMEs usually treat one business as one system.
2. One-day delivery benefits from fewer role/membership edge cases.
3. Permission enforcement is simpler.
4. Tenant isolation is easier to test.
5. The first security priority is preventing cross-tenant access, not supporting cross-tenant users.

---

## 6.3 Future migration path

The single-org model must not block future multi-org support.

When needed, the future migration path is:

```txt
Current:
User.orgId
UserRole.userId + Role.orgId

Future:
User
OrganizationMembership
MembershipRole or UserRole scoped through membership
```

Possible future schema:

```prisma
model OrganizationMembership {
  id        String   @id @default(cuid())
  userId    String
  orgId     String
  status    String   @default("active")
  createdAt DateTime @default(now())

  user User @relation(fields: [userId], references: [id])
  org  Organization @relation(fields: [orgId], references: [id])

  @@unique([userId, orgId])
  @@map("organization_memberships")
}
```

Do not implement this in the MVP unless approved by a new ADR.

# 7. Organization Data Model

## 7.1 Required Organization model

Recommended Prisma shape:

```prisma
model Organization {
  id        String   @id @default(cuid())
  name      String
  slug      String   @unique
  logoUrl   String?
  isActive  Boolean  @default(true)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
  deletedAt DateTime?
  deletedBy String?

  subscription Subscription?
  modules      OrgModule[]
  branches     Branch[]
  departments  Department[]
  users        User[]
  roles        Role[]
  settings     Setting[]

  @@index([slug])
  @@map("organizations")
}
```

Notes:

- `slug` is globally unique.
- `isActive` controls tenant availability.
- `deletedAt` is for archival/deletion workflows.
- `isActive` is not the same as deletion.
- Organizations should not be hard-deleted in normal operations.

---

## 7.2 Organization status rules

`Organization.isActive` and `Subscription.status` work together.

Recommended behavior:

| Organization state | Subscription state | Access behavior |
|---|---|---|
| `isActive = true` | `trial` | Allow access |
| `isActive = true` | `active` | Allow access |
| `isActive = true` | `suspended` | Show suspended account page; block modules |
| `isActive = true` | `cancelled` | Block modules; show support message |
| `isActive = false` | any | Block access |
| `deletedAt != null` | any | Block access |

The app shell should not load normal modules for suspended, cancelled, inactive, or deleted organizations.

---

## 7.3 Organization creation

An Organization can be created through:

1. founder/operator onboarding
2. self-service registration
3. future admin console
4. seed/demo setup

For MVP, registration may create an Organization, but it must do so server-side through the Kernel registration API.

Registration must create these records in one logical operation:

```txt
Supabase Auth user
Organization
Subscription
User
Admin Role
Wildcard Permission
UserRole assignment
Optional default Branch
Optional default Department
```

If the Prisma transaction fails after Supabase user creation, the Supabase Auth user must be rolled back.

# 8. Slug Rules

## 8.1 Slug generation

Use a deterministic slug function.

Example:

```ts
function toSlug(name: string): string {
  return name
    .toLowerCase()
    .trim()
    .replace(/[^a-z0-9]+/g, '-')
    .replace(/^-|-$/g, '')
}
```

Examples:

| Organization name | Slug |
|---|---|
| `ABC Hardware Trading` | `abc-hardware-trading` |
| `Dela Cruz Dental Clinic` | `dela-cruz-dental-clinic` |
| `M&M Supplies Inc.` | `m-m-supplies-inc` |

---

## 8.2 Slug collision handling

If a slug already exists, append a numeric suffix.

```txt
abc-hardware
abc-hardware-1
abc-hardware-2
```

This must happen inside a transaction or through a retry-safe unique constraint flow.

Pseudo-code:

```ts
async function generateUniqueOrgSlug(tx: Prisma.TransactionClient, orgName: string) {
  const baseSlug = toSlug(orgName)
  let slug = baseSlug
  let attempt = 0

  while (await tx.organization.findUnique({ where: { slug } })) {
    attempt += 1
    slug = `${baseSlug}-${attempt}`
  }

  return slug
}
```

---

## 8.3 Reserved slugs

The following slugs are reserved and cannot be used by Organizations:

```txt
api
auth
login
register
logout
admin
settings
support
billing
_app
_next
static
assets
favicon.ico
onedayos
kernel
system
```

The exact reserved list should live in Kernel code.

Recommended file:

```txt
src/kernel/organizations/reserved-slugs.ts
```

---

## 8.4 Slug mutability

For MVP, `orgSlug` should be treated as immutable after creation.

Do not build slug rename support yet.

Reason:

- route bookmarks may break
- support links may break
- audit trails become confusing
- module routes become harder to reason about

Future custom domains or slug rename support require a separate ADR.

# 9. Branch Data Model

## 9.1 Required Branch model

```prisma
model Branch {
  id        String    @id @default(cuid())
  orgId     String
  name      String
  address   String?
  phone     String?
  isActive  Boolean   @default(true)
  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt
  deletedAt DateTime?
  deletedBy String?

  org         Organization @relation(fields: [orgId], references: [id])
  departments Department[]
  employees   Employee[]
  warehouses  Warehouse[]

  @@unique([orgId, name])
  @@index([orgId])
  @@map("branches")
}
```

Notes:

- Branch is tenant-scoped.
- Branch names only need to be unique inside an Organization.
- `isActive` means the branch is still operational.
- `deletedAt` means the branch record is hidden/archived.
- Do not hard-delete a Branch if it is referenced by employees, warehouses, or module records.

---

## 9.2 Default branch

During initial org setup, create a default branch:

```txt
Head Office
```

This avoids early null-state friction for SMEs.

However, modules and business objects must not assume every record has a branch.

Some clients operate without branch-level tracking.

# 10. Department Data Model

## 10.1 Required Department model

```prisma
model Department {
  id        String    @id @default(cuid())
  orgId     String
  branchId  String?
  name      String
  parentId  String?
  isActive  Boolean   @default(true)
  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt
  deletedAt DateTime?
  deletedBy String?

  org      Organization @relation(fields: [orgId], references: [id])
  branch   Branch?      @relation(fields: [branchId], references: [id])
  parent   Department?  @relation("DeptParent", fields: [parentId], references: [id])
  children Department[] @relation("DeptParent")
  employees Employee[]

  @@index([orgId])
  @@index([orgId, branchId])
  @@map("departments")
}
```

---

## 10.2 Department uniqueness

Department names do not need to be globally unique.

Avoid over-strict constraints such as:

```prisma
@@unique([orgId, name])
```

Reason:

A company may have:

```txt
Makati Branch → Sales
Cebu Branch → Sales
```

If uniqueness is needed, prefer application validation based on client configuration later.

---

## 10.3 Department hierarchy

Departments may have parent departments.

Example:

```txt
Operations
  Warehouse
  Logistics
  Procurement
```

The application must prevent cycles.

Forbidden:

```txt
Operations parent = Warehouse
Warehouse parent = Operations
```

Cycle prevention can be application-level in MVP.

---

# 11. Organization Modules

## 11.1 OrgModule purpose

`OrgModule` records which modules are enabled for an Organization.

```prisma
model OrgModule {
  id        String   @id @default(cuid())
  orgId     String
  moduleId  String
  isEnabled Boolean  @default(true)
  enabledAt DateTime @default(now())

  org Organization @relation(fields: [orgId], references: [id])

  @@unique([orgId, moduleId])
  @@index([orgId])
  @@map("org_modules")
}
```

---

## 11.2 Enabled module rule

A module being registered in code does not mean it is enabled for every Organization.

Required checks:

```txt
Module registered in code
+ OrgModule row exists
+ OrgModule.isEnabled = true
+ user has permission
= module visible and usable
```

---

## 11.3 Disabled module behavior

If a user tries to access a disabled module route:

Page route:

```txt
Return notFound() or module-not-enabled page
```

API route:

```json
{
  "data": null,
  "error": {
    "code": "MODULE_NOT_ENABLED",
    "message": "This module is not enabled for this organization."
  }
}
```

Recommended status:

```txt
404 for normal users
403 for internal/admin diagnostics only
```

Do not expose a list of disabled modules to ordinary users unless they are organization admins.

# 12. Tenant Route Architecture

## 12.1 Required page route structure

Tenant-scoped pages should live under:

```txt
src/app/(platform)/[orgSlug]/...
```

Examples:

```txt
src/app/(platform)/[orgSlug]/dashboard/page.tsx
src/app/(platform)/[orgSlug]/employees/page.tsx
src/app/(platform)/[orgSlug]/settings/page.tsx
src/app/(platform)/[orgSlug]/inventory/page.tsx
```

---

## 12.2 Required platform layout behavior

The tenant layout must not manually assemble auth and org checks in every file.

Required pattern:

```tsx
export default async function OrgLayout({ children, params }: Props) {
  const { orgSlug } = await params
  const ctx = await sdk.auth.requirePageOrgContext({ orgSlug })

  return (
    <AppShell ctx={ctx}>
      {children}
    </AppShell>
  )
}
```

Forbidden pattern:

```tsx
const authUser = await requireAuth()
const org = await prisma.organization.findUnique({ where: { slug: orgSlug } })
const user = await prisma.user.findUnique({ where: { id: authUser.id } })

// Missing user.orgId === org.id check
```

---

## 12.3 Page behavior matrix

| Condition | Page behavior |
|---|---|
| No Supabase session | Redirect to `/login` |
| Supabase session but no platform User | Redirect to `/login` or show account error |
| orgSlug does not exist | `notFound()` |
| orgSlug exists but belongs to another user | `notFound()` |
| Organization inactive | Show unavailable page or `notFound()` |
| Organization suspended | Show suspended account page |
| Module disabled | `notFound()` or module-not-enabled page |
| Permission denied inside valid org | Permission denied page |

Why `notFound()` for cross-org access?

To avoid confirming that another Organization exists.

# 13. Tenant API Architecture

## 13.1 Required API route structure

Tenant-scoped APIs should live under:

```txt
/api/orgs/[orgSlug]/...
```

Examples:

```txt
/api/orgs/[orgSlug]/employees
/api/orgs/[orgSlug]/settings
/api/orgs/[orgSlug]/inventory/products
/api/orgs/[orgSlug]/inventory/stock-movements
```

Avoid:

```txt
/api/employees?orgId=...
/api/inventory/products?orgId=...
/api/[module]?orgId=...
```

---

## 13.2 Required API context pattern

Every tenant-scoped API route must start by resolving API org context.

Recommended pattern:

```ts
export async function GET(
  req: NextRequest,
  { params }: { params: Promise<{ orgSlug: string }> }
) {
  const { orgSlug } = await params
  const ctxResult = await sdk.auth.requireApiOrgContext(req, { orgSlug })

  if (!ctxResult.ok) {
    return sdk.api.error(ctxResult.error)
  }

  const ctx = ctxResult.ctx

  const employees = await EmployeeService.list(ctx)

  return sdk.api.ok(employees)
}
```

The exact helper names may be finalized in the SDK document, but the pattern is mandatory.

---

## 13.3 API behavior matrix

| Condition | API status | Error code |
|---|---:|---|
| No session | `401` | `UNAUTHENTICATED` |
| Session but no platform User | `401` or `403` | `USER_NOT_PROVISIONED` |
| orgSlug does not exist | `404` | `ORG_NOT_FOUND` |
| orgSlug belongs to another user | `404` | `ORG_NOT_FOUND` or `ORG_ACCESS_DENIED` hidden as 404 |
| Organization inactive | `403` | `ORG_INACTIVE` |
| Organization suspended | `403` | `ORG_SUSPENDED` |
| Module disabled | `404` or `403` | `MODULE_NOT_ENABLED` |
| Permission denied | `403` | `FORBIDDEN` |
| Validation failed | `400` | `VALIDATION_ERROR` |

All API errors must use the standard shape:

```json
{
  "data": null,
  "error": {
    "code": "FORBIDDEN",
    "message": "You do not have permission to perform this action."
  }
}
```

# 14. PlatformContext Contract

## 14.1 Required type

Recommended initial shape:

```ts
declare const verifiedPlatformContext: unique symbol

export type PlatformContext = {
  readonly [verifiedPlatformContext]: true

  readonly authUserId: string
  readonly userId: string
  readonly userEmail: string
  readonly userName: string
  readonly userIsActive: boolean

  readonly orgId: string
  readonly orgSlug: string
  readonly orgName: string
  readonly orgIsActive: boolean

  readonly subscription: {
    readonly plan: 'starter' | 'pro' | 'enterprise'
    readonly status: 'trial' | 'active' | 'suspended' | 'cancelled'
    readonly maxUsers: number
    readonly maxModules: number
    readonly storageGb: number
  } | null

  readonly enabledModuleIds: readonly string[]

  readonly roleIds: readonly string[]
  readonly roleNames: readonly string[]

  readonly requestId?: string
}
```

The unique symbol brand makes it harder for ordinary code to fabricate a context object accidentally.

Only Kernel auth/context helpers should create `PlatformContext`.

---

## 14.2 Context creation rules

`PlatformContext` may only be created after:

```txt
Supabase session verified
Prisma User loaded from session user ID
Organization loaded from orgSlug
user.orgId === org.id verified
User is active
Organization is active
Organization is not deleted
Subscription status checked
Enabled modules loaded
User roles loaded
```

---

## 14.3 Context usage rules

Required service pattern:

```ts
export class EmployeeService {
  static async list(ctx: PlatformContext) {
    const db = sdk.getDb(ctx)

    return db.employee.findMany({
      where: {
        orgId: ctx.orgId,
        deletedAt: null,
      },
    })
  }
}
```

Forbidden service pattern:

```ts
export class EmployeeService {
  static async list(orgId: string) {
    return sdk.getDb(orgId).employee.findMany({ where: { orgId } })
  }
}
```

`orgId: string` is too easy to misuse.

# 15. SDK Requirements

The SDK must expose tenant-safe helpers.

Minimum required APIs:

```ts
sdk.auth.requirePageOrgContext({ orgSlug })
sdk.auth.requireApiOrgContext(request, { orgSlug })
sdk.organizations.getCurrent(ctx)
sdk.organizations.requireActive(ctx)
sdk.modules.requireEnabled(ctx, moduleId)
sdk.getDb(ctx)
```

Potential API helper:

```ts
sdk.api.ok(data)
sdk.api.error(error)
```

The exact SDK shape should be frozen in the SDK document, but the tenancy behavior is mandatory.

# 16. Database Access Rules

## 16.1 No raw Prisma in modules

Modules must not import:

```ts
import { prisma } from '@/kernel/db/client'
```

Modules must use:

```ts
import { sdk } from '@/sdk'

const db = sdk.getDb(ctx)
```

---

## 16.2 `sdk.getDb(ctx)` replaces `sdk.getDb(orgId)`

Earlier planning used:

```ts
sdk.getDb(orgId)
```

For the restarted build, use:

```ts
sdk.getDb(ctx)
```

Reason:

A verified context is safer than a loose string.

This preserves the future database-routing seam while reducing the chance that Claude or future engineers accidentally pass a client-supplied `orgId`.

---

## 16.3 Tenant-scoped unique constraints

Any tenant-owned code or name should be unique inside the Organization, not globally.

Examples:

```prisma
@@unique([orgId, employeeNo])
@@unique([orgId, code])
@@unique([orgId, module, key])
@@unique([orgId, moduleId])
```

Avoid globally unique business values unless required by the product.

---

## 16.4 Tenant indexes

Every tenant-scoped table should have an `orgId` index.

Required:

```prisma
@@index([orgId])
```

For common filtered queries, add composite indexes.

Examples:

```prisma
@@index([orgId, deletedAt])
@@index([orgId, branchId])
@@index([orgId, departmentId])
@@index([orgId, createdAt])
```

Do not over-index before real query patterns exist.

---

# 17. Client Payload Rules

## 17.1 Create payloads must omit orgId

Good schema:

```ts
const CreateEmployeeSchema = z.object({
  employeeNo: z.string().min(1),
  name: z.string().min(1),
  email: z.string().email().optional(),
  branchId: z.string().optional(),
  departmentId: z.string().optional(),
})
```

Bad schema:

```ts
const CreateEmployeeSchema = z.object({
  orgId: z.string(),
  employeeNo: z.string(),
  name: z.string(),
})
```

---

## 17.2 Update payloads must omit orgId

Good schema:

```ts
const UpdateEmployeeSchema = CreateEmployeeSchema.partial()
```

Bad schema:

```ts
const UpdateEmployeeSchema = z.object({
  orgId: z.string().optional(),
  name: z.string().optional(),
})
```

---

## 17.3 If orgId appears in payload, reject it

Do not silently ignore unexpected `orgId` fields if strict validation is available.

Recommended Zod behavior:

```ts
const schema = z.object({
  name: z.string(),
}).strict()
```

If the client submits:

```json
{
  "name": "Juan",
  "orgId": "other-org"
}
```

The API should return:

```json
{
  "data": null,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Unexpected field: orgId"
  }
}
```

This catches mistakes early.

## 18.2 Bad page example

```tsx
import { requireAuth } from '@/kernel/auth/session'
import { prisma } from '@/kernel/db/client'

export default async function EmployeesPage({ params }: Props) {
  const { orgSlug } = await params
  await requireAuth()

```

Problems:

- module/page imports Kernel internals
- no user/org membership check
- no `PlatformContext`
- no subscription/module/permission path

---

## 18.3 Good API example

```ts
import { sdk } from '@/sdk'
import { EmployeeService } from '@/modules/hr/employees/service'

export async function POST(req: NextRequest, { params }: Props) {
  const { orgSlug } = await params

  const ctxResult = await sdk.auth.requireApiOrgContext(req, { orgSlug })
  if (!ctxResult.ok) return sdk.api.error(ctxResult.error)

  const ctx = ctxResult.ctx

  const permission = await sdk.permissions.require(ctx, {
    module: 'kernel',
    action: 'create',
    resource: 'employee',
  })
  if (!permission.ok) return sdk.api.error(permission.error)

  const body = await req.json()
  const parsed = CreateEmployeeSchema.safeParse(body)
  if (!parsed.success) return sdk.api.validationError(parsed.error)

  const employee = await EmployeeService.create(ctx, parsed.data)

  return sdk.api.created(employee)
}
```

---

## 18.4 Bad API example

```ts
export async function POST(req: NextRequest) {
  await sdk.auth.requireAuth()

  const body = await req.json()
  const employee = await EmployeeService.create({
    orgId: body.orgId,
    name: body.name,
  })

  return NextResponse.json({ data: employee, error: null })
}
```

Problems:

- redirect-style auth may return HTML instead of JSON
- accepts client-supplied `orgId`
- no orgSlug route context
- no tenant membership validation
- no permission check

# 19. Organization Settings

Organization-level settings should use the Kernel `Setting` model.

Example:

```prisma
model Setting {
  id        String   @id @default(cuid())
  orgId     String
  module    String
  key       String
  value     Json
  updatedAt DateTime @updatedAt

  org Organization @relation(fields: [orgId], references: [id])

  @@unique([orgId, module, key])
  @@index([orgId])
  @@map("settings")
}
```

Examples:

```txt
module = kernel
key = timezone
value = "Asia/Manila"

module = kernel
key = date_format
value = "MM/dd/yyyy"

module = inventory
key = default_warehouse_id
value = "warehouse_123"
```

Settings are tenant-scoped.

Do not store organization settings in environment variables.

If the customer cancels:

```txt
Subscription.status = cancelled
```

Behavior:

- block module access
- preserve data for retention period
- allow export only if policy permits
- do not hard-delete immediately

---

## 20.5 Inactive organization

If:

```txt
Organization.isActive = false
```

Behavior:

- block normal access
- do not show modules
- return safe unavailable response

## 20.6 Deleted/archived organization

If:

```txt
Organization.deletedAt != null
```

Behavior:

- organization should not appear in normal lookups
- tenant route should not load
- data should remain until retention/deletion policy is executed

Hard deletion requires separate operational approval.

# 22. RLS Position

PostgreSQL Row Level Security is deferred.

However, this document must not be interpreted as saying RLS is unnecessary.

MVP rule:

```txt
Application-layer tenant isolation is mandatory now.
RLS is future defense-in-depth.
```

Future RLS direction:

```sql
current_setting('app.org_id')
```

Potential approach:

```txt
Set app.org_id at transaction/session level
Apply RLS policy to tenant-scoped tables
Keep application-level ctx.orgId checks anyway
```

Do not implement RLS until the Data/Tenancy/RLS document is written and frozen.

# 29. Architectural Warnings

## 29.1 The old bug must not reappear

The previous MVP risk was not that organizations did not exist.

The risk was that authenticated users could reach organization routes without complete membership checks.

The restarted build must make this impossible by using one canonical context helper.

---

## 29.2 Do not scatter tenant checks

Bad architecture:

```txt
Every page manually checks orgSlug differently.
Every API manually checks orgSlug differently.
Every module manually checks orgId differently.
```

Good architecture:

```txt
Kernel creates PlatformContext once.
Everything else consumes PlatformContext.
```

---

## 29.3 Tenant isolation is not just read protection

Tenant isolation must protect:

- reads
- creates
- updates
- deletes
- relation IDs
- event payloads
- search results
- reports
- exports
- AI context
- background jobs

Do not treat tenant isolation as a simple `findMany({ where: { orgId } })` habit.

It is a platform invariant.

---

# 30. Summary

OneDayOS tenancy is built around this invariant:

```txt
No PlatformContext, no tenant access.
```

Every protected route, API, service, module, query, event, report, export, and future AI operation must be scoped through verified tenant context.

For MVP:

```txt
User belongs to one Organization.
Organization is located by orgSlug.
Access is granted only if user.orgId === organization.id.
Services receive PlatformContext.
Database access uses sdk.getDb(ctx).
Client-supplied orgId is rejected.
```

This is the foundation that allows OneDayOS to safely run many SMEs on one shared platform.
