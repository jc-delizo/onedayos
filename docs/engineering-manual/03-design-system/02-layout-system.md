# 1. Purpose

This document defines the **layout system** for OneDayOS.

The layout system is the structure every OneDayOS screen inherits:

```txt
Auth shell
Platform shell
Organization shell
Sidebar
Header
Page header
Content region
Toolbars
Panels
Detail layouts
Settings layouts
Module layouts
Business Object layouts
```

The purpose is to make OneDayOS feel like **one coherent Business Operating System**, not a collection of unrelated pages generated by Claude.

A module developer or AI coding agent should not invent layout patterns. They should compose screens inside the layout system defined here.

---

# 2. Core Position

OneDayOS uses a **single shared platform layout**.

```txt
One codebase
One app shell
One organization shell
Many client organizations
Many enabled modules
Consistent layout everywhere
```

Clients do not get custom app shells, custom sidebars, custom layout systems, or per-client UI forks.

A client may receive light branding configuration later, such as logo or brand accent, but the application structure remains OneDayOS.

---

# 3. Design Goals

The OneDayOS layout should feel:

```txt
premium
calm
fast
data-dense
keyboard-friendly
businesslike
modular
consistent
```

The layout should make daily business operations feel efficient.

It should not feel like:

```txt
a generic admin dashboard
a SaaS starter template
a Bootstrap ERP clone
a marketing landing page
a toy no-code builder
a random collection of generated CRUD pages
```

---

# 4. Layout Principles

## 4.1 Consistency over novelty

Every module should feel like it belongs to the same product.

Inventory, Leave, CRM, Assets, Expenses, and future modules should not invent different page structures.

```txt
Bad:
Inventory has a left toolbar.
CRM has a top tab bar.
Leave has floating buttons.
Assets has card-only navigation.

Good:
All modules use the same shell, page header, toolbar, table, form, and detail patterns.
```

## 4.2 Data first, decoration second

Business applications are used to complete tasks, not admire decorative UI.

Layout should prioritize:

```txt
clear hierarchy
fast scanning
dense tables
usable forms
visible status
obvious actions
low cognitive load
```

## 4.3 Shell is stable; content changes

Users should always know where they are.

The shell should not shift dramatically between modules.

```txt
Sidebar stays stable.
Header stays stable.
Page actions stay in predictable places.
Tables use the same layout rules.
Forms use the same layout rules.
```

## 4.4 Server-resolved layout state

Security-sensitive layout information must be resolved server-side.

This includes:

```txt
current organization
current user
enabled modules
permissions
visible navigation
subscription/module availability
```

Client components may render resolved layout data, but they must not discover permissions or modules independently.

## 4.5 Layout must support future generation

Claude and future generators should be able to create module pages quickly because the layout contract is stable.

The goal is not to make module creation slower.

The goal is to remove repeated decisions.

---

# 5. Non-Goals

This document does not define:

```txt
component visual variants
full brand token system
detailed table behavior
detailed form behavior
dashboard metrics design
mobile app navigation
public marketing website layout
client portal layout
custom per-client layouts
```

Those belong in separate documents.

This document defines the structural layout system used by the authenticated OneDayOS application.

# 6. Route Layout Model

## 6.1 Top-level route groups

The restarted OneDayOS platform should use a route structure similar to:

```txt
src/app/
  (auth)/
    login/page.tsx
    register/page.tsx
    layout.tsx

  (platform)/
    [orgSlug]/
      layout.tsx
      dashboard/page.tsx
      objects/
        products/page.tsx
        customers/page.tsx
        employees/page.tsx
        suppliers/page.tsx
        warehouses/page.tsx
      inventory/
        page.tsx
        stock-levels/page.tsx
        adjustments/page.tsx
      leave/
        page.tsx
        requests/page.tsx
      settings/
        page.tsx
```

The authenticated platform lives under:

```txt
/[orgSlug]/...
```

The `orgSlug` identifies the organization route context, but it is not authorization.

Authorization comes from verified `PlatformContext`.

## 6.2 Auth routes

Auth routes use a separate layout.

```txt
/(auth)/login
/(auth)/register
```

Auth screens should be calm, focused, and minimal.

They should not use the full platform shell.

## 6.3 Platform routes

All authenticated business routes should live inside the organization shell.

```txt
/[orgSlug]/dashboard
/[orgSlug]/objects/products
/[orgSlug]/inventory/stock-levels
/[orgSlug]/leave/requests
/[orgSlug]/settings
```

No tenant-scoped business page should exist outside an organization route.

```txt
Forbidden:
/inventory
/products
/dashboard
/settings
```

Those routes lack tenant context.

# 7. Master Shell Architecture

The OneDayOS shell has four layers:

```txt
Root App
  ↓
Auth / Platform Route Group
  ↓
Organization Shell
  ↓
Page Layout
```

Authenticated business pages should render inside:

```txt
OrganizationShell
  AppSidebar
  MainColumn
    TopHeader
    PageContent
```

Recommended structure:

```txt
<div className="h-screen overflow-hidden">
  <AppSidebar />
  <div className="flex min-w-0 flex-1 flex-col">
    <TopHeader />
    <main>
      {children}
    </main>
  </div>
</div>
```

The shell should occupy the full viewport height.

The main content area should scroll independently.

The sidebar should not scroll the whole page unless its own content overflows.

# 8. Organization Shell

## 8.1 Purpose

The organization shell is responsible for resolving and displaying the current tenant context.

It must load:

```txt
current authenticated user
current OneDayOS User
current Organization
verified PlatformContext
visible navigation
module enablement state
permission-aware navigation
subscription status
```

## 8.2 Security boundary

The organization shell must not merely find the organization by slug.

It must verify membership.

```txt
Required:
org = find org by orgSlug
user = find current platform user
assert user.orgId === org.id
create PlatformContext
```

If membership fails, return safe `404`, not a permission-revealing message.

## 8.3 Suspended organization behavior

If an organization is suspended:

```txt
user may log in
organization shell may render limited suspended-state UI
business modules should be blocked
settings/billing/support pages may remain available depending on future policy
```

The shell should not pretend modules are available when the subscription is suspended.

## 8.4 Server component requirement

The organization layout should be a server component.

It may pass safe resolved props to client shell components.

```tsx
// Server component
export default async function OrgLayout({ children, params }) {
  const ctx = await sdk.auth.requirePageOrgContext(params.orgSlug)
  const navigation = await sdk.navigation.getVisibleNavigation(ctx)

  return (
    <OrganizationShell
      org={safeOrgView}
      user={safeUserView}
      navigation={navigation}
    >
      {children}
    </OrganizationShell>
  )
}
```

Client shell components must not import:

```txt
@/sdk/server
@/kernel/*
raw Prisma
server env helpers
```

# 9. Sidebar Layout

## 9.1 Sidebar purpose

The sidebar is the primary persistent navigation surface.

It shows:

```txt
OneDayOS identity
current organization context
core platform navigation
Business Object navigation
enabled module navigation
settings/support links
collapse control
```

It should make the platform feel stable and operational.

## 9.2 Sidebar width

Recommended desktop widths:

```txt
Expanded sidebar: 256px
Collapsed sidebar: 64px
Header height: 56px
Main content padding: 24px default
```

These numbers may be adjusted in the final component implementation, but should remain consistent globally.

## 9.3 Sidebar sections

Recommended sidebar sections:

```txt
Brand / organization switch area
Core
Business Objects
Modules
System
```

Example:

```txt
OneDayOS
Acme Trading

Core
  Dashboard

Records
  Employees
  Products
  Customers
  Suppliers
  Warehouses

Modules
  Inventory
  Leave
  CRM
  Assets

System
  Settings
  Help / Support
```

Do not dump every page into one flat list.

## 9.4 Business Object navigation

Business Object navigation must not be owned by a module.

```txt
Products are not under Inventory by ownership.
Customers are not under CRM by ownership.
Employees are not under Leave by ownership.
Suppliers are not under Purchasing by ownership.
Warehouses are not under Inventory by ownership.
```

The UI may provide contextual shortcuts from modules, but the primary shared-object pages should live in the Business Objects area.

Recommended routes:

```txt
/[orgSlug]/objects/products
/[orgSlug]/objects/customers
/[orgSlug]/objects/employees
/[orgSlug]/objects/suppliers
/[orgSlug]/objects/warehouses
```

## 9.5 Module navigation

Module navigation is generated from module manifest metadata, then filtered server-side.

Visibility requires:

```txt
authenticated user
valid tenant membership
module enabled for organization
user permission for the nav item
subscription permits access
```

Module navigation should not be hard-coded into the sidebar component.

## 9.6 Active state matching

Sidebar active states must use segment-aware matching.

Do not use raw prefix matching.

```ts
// Forbidden
pathname.startsWith(href)
```

Because:

```txt
/inventory matches /inventory-audit
/settings matches /settings-advanced unexpectedly
```

Use route segments or a helper such as:

```ts
isActiveRoute(pathname, href)
```

Expected behavior:

```txt
/current: /acme/inventory
href:     /acme/inventory
active:   true

/current: /acme/inventory/stock-levels
href:     /acme/inventory
active:   true

/current: /acme/inventory-audit
href:     /acme/inventory
active:   false
```

## 9.7 Sidebar collapse behavior

Desktop sidebar may support collapse.

Collapsed sidebar should show:

```txt
logo/icon
icons
tooltips for labels
active state
```

Collapsed sidebar must not hide navigation in a way that makes the app unusable.

## 9.8 Mobile sidebar behavior

For small screens, the sidebar should become a sheet/drawer triggered from the header.

MVP can prioritize desktop/tablet, but mobile should not be completely broken.

Minimum mobile behavior:

```txt
header menu button opens navigation drawer
navigation drawer closes after selecting a link
forms remain usable
critical actions remain accessible
```

# 10. Top Header Layout

## 10.1 Header purpose

The top header provides persistent context and global actions.

Recommended contents:

```txt
breadcrumb or page location
organization indicator
optional global search / command trigger later
user menu
support/help entry
```

## 10.2 Header height

Recommended height:

```txt
56px
```

Header should feel compact.

Do not create oversized marketing-style headers.

## 10.3 User menu

User menu should include:

```txt
user name
email
profile/account link future
support/help link future
sign out
```

Do not place sensitive admin actions in the user menu unless explicitly designed later.

## 10.4 Organization display

The header may show current organization name or slug.

MVP assumes one org per user, so full org switching is deferred.

Do not build an organization switcher unless multi-org users are implemented through a future ADR.

## 10.5 Global search / command menu

A command menu may come later.

For MVP, reserve space or keyboard convention, but do not implement global business-data search unless Search Service is approved.

Allowed early command-menu behavior:

```txt
navigate to pages
open settings
open help
quick create if permission allows
```

Deferred:

```txt
cross-module data search
AI search
semantic search
raw business record search
```

# 11. Main Content Region

## 11.1 Content container

The main content area should be consistent across pages.

Recommended defaults:

```txt
padding: 24px desktop
padding: 16px tablet/mobile
max-width: usually none for tables/dashboards
max-width: constrained for forms/settings
```

Business applications often need horizontal space. Do not force all content into narrow marketing-style containers.

## 11.2 Page width patterns

Use width based on page type:

| Page Type | Width Pattern |
|---|---|
| Dashboard | full available width |
| Table/list | full available width |
| Detail page | full width with structured panels |
| Create/edit form | constrained, usually 720px–960px |
| Settings page | split layout, constrained content |
| Wizard/onboarding | constrained, centered within shell |

## 11.3 Scroll behavior

The sidebar and header should remain stable.

The main content region scrolls.

Avoid body-level page scrolling where the shell disappears.

Recommended:

```txt
h-screen shell
overflow-hidden root
main overflow-auto
```

## 11.4 Content density

OneDayOS should be data-dense but not cramped.

Use compact spacing for business records and table-heavy pages.

Avoid oversized card grids with low information density.

# 12. Page Layout Pattern

Every standard page should follow this structure:

```txt
PageHeader
  title
  description / subtitle
  breadcrumbs optional
  primary action
  secondary actions

PageToolbar optional
  search
  filters
  view controls
  bulk actions

PageBody
  table / form / dashboard / detail panels
```

## 12.1 Page header

The page header should provide:

```txt
where am I?
what is this page for?
what is the most important action?
```

Example:

```txt
Products
Manage the shared product catalog used by Inventory, Purchasing, and Sales.
[New Product]
```

## 12.2 Primary action placement

Primary page actions should appear on the right side of the page header.

Examples:

```txt
New Product
New Stock Adjustment
New Leave Request
New Customer
```

Do not scatter primary actions randomly inside cards.

## 12.3 Secondary actions

Secondary actions may appear near the primary action or in a dropdown.

Examples:

```txt
Import
Export
Settings
Archive
```

Remember:

```txt
Read permission is not export permission.
Create permission is not import permission.
```

## 12.4 Descriptions

Page descriptions should be short and useful.

Avoid generic filler like:

```txt
Manage your records here.
```

Prefer:

```txt
Products are shared across Inventory, Purchasing, and future Sales workflows.
```

# 13. Standard Page Types

## 13.1 Dashboard pages

Dashboard pages should not be generic card dumps.

A dashboard should answer:

```txt
What changed?
What needs attention?
What should I do next?
```

MVP dashboards may be simple, but they should not use fake metrics or placeholder charts.

Allowed MVP dashboard content:

```txt
empty state
setup checklist
recent relevant records if real
module shortcuts
attention items if real
```

Forbidden:

```txt
random stat cards with fake values
meaningless charts
marketing-style hero sections
wall of cards copied from SaaS starter templates
```

## 13.2 List/table pages

List pages are core operational screens.

They should use:

```txt
page header
toolbar
data table
empty state
pagination / load state
row actions
bulk actions when appropriate
```

Tables must inherit the design system table standards.

## 13.3 Create/edit pages

Create and edit pages should be calm and focused.

Recommended pattern:

```txt
PageHeader
FormPanel
Sticky footer/actions if form is long
```

Forms should not feel like raw database tables.

Never include hidden `orgId` fields.

Tenant identity comes from verified server context.

## 13.4 Detail pages

Detail pages should use structured sections.

Recommended pattern:

```txt
RecordHeader
  title
  status
  key metadata
  actions

Content
  main details
  related module panels
  activity/timeline placeholder only if service exists
```

Do not implement Activity Feed, Comments, Attachments, or Audit Log UI unless those services exist.

## 13.5 Settings pages

Settings pages should use a two-level structure:

```txt
SettingsShell
  SettingsSidebar / tabs
  SettingsContent
```

Settings should distinguish:

```txt
organization settings
user/account settings
module settings
billing/subscription settings
security settings
```

Do not dump all settings into one long form.

## 13.6 Permission denied pages

Permission-denied pages should be clear and calm.

They should say:

```txt
You do not have permission to access this page.
Contact your administrator if you believe this is a mistake.
```

Do not reveal sensitive record names or other organizations.

Wrong-tenant access should usually return safe `404`, not a permission-denied screen.

---

# 14. Business Object Layout Rules

Business Object pages should look and feel shared.

Examples:

```txt
Employees
Products
Customers
Suppliers
Warehouses
```

These pages should not be visually branded as a module.

For example:

```txt
Product page should not say "Inventory Products".
Customer page should not say "CRM Customers".
Employee page should not say "Leave Employees".
```

Modules may link to Business Object pages contextually.

Example:

```txt
Inventory Stock Level row links to Product detail.
CRM Opportunity links to Customer detail.
Leave Request links to Employee detail.
```

But ownership remains clear.

---

# 15. Module Layout Rules

Each module should have a consistent internal landing page.

Recommended module index:

```txt
/[orgSlug]/inventory
/[orgSlug]/leave
/[orgSlug]/crm
```

The module landing page should provide:

```txt
module-specific overview
important actions
primary records
attention states
links to module subpages
```

But avoid fake dashboard content.

## 15.1 Module subnavigation

For modules with multiple subpages, use one of these patterns:

```txt
sidebar nested items
page-level tabs
section cards on module landing page
```

Do not let every module invent a different subnavigation style.

## 15.2 Module routes

Module pages live under:

```txt
/[orgSlug]/[moduleId]/...
```

Examples:

```txt
/[orgSlug]/inventory/stock-levels
/[orgSlug]/inventory/adjustments
/[orgSlug]/leave/requests
/[orgSlug]/crm/opportunities
```

Module APIs live under:

```txt
/api/orgs/[orgSlug]/[moduleId]/...
```

Never use:

```txt
/api/[module]?orgId=...
```

# 16. Responsive Layout

## 16.1 Desktop first, not desktop only

OneDayOS is primarily a business desktop/tablet application.

But basic mobile usability is still required.

## 16.2 Breakpoints

Recommended behavior:

```txt
>= 1024px: persistent sidebar + header
768px–1023px: collapsible sidebar or narrower shell
< 768px: sidebar drawer + simplified header
```

## 16.3 Tables on small screens

For small screens:

```txt
allow horizontal scroll for dense tables
keep headers readable
avoid hiding critical status/actions
consider card-like row summaries only if defined later
```

Do not create a completely separate mobile UI for MVP.

## 16.4 Forms on small screens

Forms should stack vertically on small screens.

Primary actions should remain reachable.

Long forms may use sticky bottom actions later.

---

# 17. Keyboard and Interaction Layout Rules

OneDayOS should be keyboard-friendly.

Layout should support:

```txt
Tab navigation
visible focus states
Escape to close dialogs/drawers
Enter to submit safe forms
Cmd/Ctrl+K reserved for command menu future
```

Do not trap focus incorrectly.

Do not remove focus outlines.

The layout should make keyboard navigation predictable across modules.

---

# 18. Loading, Empty, and Error Layout Placement

This document does not define full states, but it defines where they appear.

## 18.1 Loading states

Loading states should appear inside the content region that is loading.

Do not blank the whole app shell for page-level content loading.

Use skeletons over spinners.

## 18.2 Empty states

Empty states should appear in the table/body region.

They should explain the next action when appropriate.

Example:

```txt
No products yet.
Create your first product to start using Inventory and Purchasing workflows.
[New Product]
```

## 18.3 Error states

Errors should appear at the appropriate scope:

```txt
form field error
form-level error
panel error
page error
app-level error
```

Do not use only toast messages for important persistent failures.

Recommended component structure:

src/components/platform/layout/

# 20. Server / Client Split

## 20.1 Server responsibilities

Server components/helpers resolve:

```txt
PlatformContext
current organization
current user
visible navigation
module enablement
permissions
subscription state
initial page data
```

## 20.2 Client responsibilities

Client components handle:

```txt
collapse state
drawer open state
menus
tabs
dialogs
interactive tables
form inputs
optimistic UI
```

Client components receive safe data as props.

They do not fetch permission state from scratch unless explicitly approved.

## 20.3 Forbidden client imports

Client components must not import:

```txt
@/sdk/server
@/kernel/*
@/kernel/db/client
raw Prisma
server env helpers
Supabase service role helpers
```

# 21. Multi-Tenant Layout Rules

Layout must never rely on client-supplied tenant identity.

```txt
Forbidden:
hidden orgId inputs
localStorage orgId
query string orgId
client-side org selection without server verification
```

Allowed:

```txt
orgSlug in route
server resolves org by slug
server verifies user belongs to org
server creates PlatformContext
server passes safe org view to layout
```

The layout should reinforce tenancy visually without exposing sensitive internals.

Show:

```txt
organization name
maybe organization logo
```

Do not show:

```txt
orgId
internal database IDs
service/account metadata
```

---

# 22. Subscription and Module Availability Layout

Module availability has multiple layers:

```txt
module exists in codebase
module enabled for organization
module allowed by subscription
user has permission
```

The layout should handle these states consistently.

## 22.1 Module not enabled

For normal users, disabled modules should not appear in navigation.

Direct access should return safe `404 MODULE_NOT_FOUND`.

## 22.2 Module enabled but no permission

Navigation item should usually be hidden.

Direct access should show permission-denied behavior or `403`, depending on route type.

## 22.3 Module unavailable by plan

Future plan-gated modules may show an admin-only upgrade prompt.

Do not show upgrade prompts to normal staff users unless explicitly designed.

---

# 23. Client Branding Layout Rules

Normal client branding may include:

```txt
organization logo
organization name
small brand accent configuration later
```

Normal client branding must not include:

```txt
custom sidebar layout
custom navigation structure
custom components
custom CSS per client
custom typography
custom dashboard layout
per-client shell forks
```

Dedicated/premium deployments may have different branding later, but that requires separate product and pricing decisions.

---

# 24. Anti-Patterns

Claude must not generate these layout patterns:

```txt
Generic SaaS dashboard with fake stats
Marketing-style hero inside business app shell
Per-module custom sidebar
Per-client custom layout fork
Cards-only CRUD pages with no tables
Raw database table layout with no product hierarchy
Hidden orgId fields in forms
Client-side permission discovery for navigation
Sidebar links to routes that do not exist
pathname.startsWith(href) active-state matching
Business Objects nested under one module as if owned by it
Full-page spinner replacing the whole shell
Random page padding per module
Different button/action placement per module
Unapproved command-menu search across business data
Mobile layout that makes forms unusable
```

---

# 25. Required Layout Tests

Layout implementation must include tests for:

```txt
organization shell rejects wrong-org user
sidebar only shows enabled modules
sidebar filters unauthorized nav items
sidebar active matching does not match sibling prefixes
Business Object nav is separate from module nav
module nav uses manifest data
client components do not import server-only SDK/kernel code
mobile drawer opens and closes
page header renders primary action consistently
forms do not include hidden orgId inputs
```

At minimum, the old `pathname.startsWith(href)` bug must not return.

# 26. Claude Implementation Rules

Claude may implement layout only after this document is approved.

Claude must:

```txt
use the approved shell structure
resolve layout data server-side
use PlatformContext
use server-filtered navigation
use segment-aware active matching
keep Business Object nav separate from module nav
use shared layout components
include layout tests
avoid per-module layout invention
avoid per-client layout forks
```

Claude must not:

```txt
use raw startsWith active matching

use client-supplied orgId
fetch permissions entirely client-side

create missing-route sidebar links
create custom shells per module
implement global search or command data search without approval
```

# 28. Founder Review Questions

Before freezing this document, answer:

```txt
1. Do we want Business Objects visible as a top-level sidebar section called Records?
2. Should module navigation be flat at first, or support nested items immediately?
3. Should the sidebar default to expanded for all desktop users?
4. Should dashboard be organization-wide first, or module-specific dashboards first?
5. Should settings use sidebar navigation, tabs, or both?
6. Should client logo appear in the sidebar, header, or both?
7. Should OneDayOS keep the same shell for all modules, including future premium modules?
```

Recommended founder defaults:

```txt
1. Yes, use Records for shared Business Objects.
2. Support one nesting level, but keep MVP simple.
3. Expanded by default.
4. Organization-wide dashboard first, module dashboards later.
5. Settings sidebar for desktop, tabs/drawer for mobile.
6. Client logo in sidebar if available; org name in header/sidebar.
7. Yes, same shell for all normal modules.
```

# 29. Final Rule

The OneDayOS layout should make every module feel like part of one operating system.

```txt
The sidebar teaches the platform.
The header stabilizes context.
The page header clarifies purpose.
The content region enables work.
The layout never invents security.
```

A page is not acceptable because it renders.

It is acceptable when a user instantly understands:

```txt
where they are
what data they are looking at
what action they can take
why they can or cannot take it
how it fits into OneDayOS
```

# ADR-0011 Page Pattern Amendment

`03-design-system/10-page-patterns.md` defines the shared page patterns that future pages and modules must use after Founder review.

Layout requirements clarified by ADR-0011:

```txt
[ ] Authenticated pages use the persistent app shell as primary navigation.
[ ] Content-local navigation must not duplicate or replace the app shell.
[ ] Page headers are shared and consistent: breadcrumb, title, description, action.
[ ] Loading states are contextual to the page pattern.
[ ] Error, empty, permission, and unavailable states explain recovery.
[ ] Process Flow pages teach module workflow and boundaries.
```

The shell explains the operating system. Page content explains the current task.
