# 1. Purpose

This document defines how OneDayOS API routes must be tested.

API tests are not optional. In OneDayOS, API routes are one of the most important security boundaries because they are the point where external input enters the platform.

A OneDayOS API route is not complete just because it works for the correct user.

It is complete only when it also fails safely for:

```txt
unauthenticated users
users from the wrong organization
users without permission
users whose module is disabled
invalid request bodies
invalid route parameters
client-supplied orgId attempts
soft-deleted records
malformed query strings
unexpected errors
```

API testing exists to prove that the restarted OneDayOS build does not recreate the old MVP risks:

```txt
redirect-style API auth
HTML login responses from API routes
auth-only APIs without permission enforcement
incomplete organization membership checks
loose orgId handling
/api/[module]?orgId=... route shapes
raw Prisma shortcuts
unsafe generated APIs
weak placeholder tests
```

---

# 2. Core Rule

```txt
A OneDayOS API route is done only when its denial paths are tested.
```

The happy path is necessary, but not enough.

For every protected API route, tests must prove:

```txt
right user succeeds
wrong user fails
wrong organization fails
missing auth fails
missing permission fails
invalid input fails
client-supplied orgId fails
response shape is stable
```

# 5. Required API Response Contract

All API tests must enforce the Kernel API contract.

Every API response must be JSON.

Allowed shape:

```ts
type ApiResponse<T> = {
  data: T | null
  error: ApiError | null
  meta?: Record<string, unknown>
}
```

Where:

```ts
type ApiError = {
  code: string
  message: string
  details?: unknown
}
```

APIs must not return:

```txt
HTML login pages
Next.js redirect responses
raw stack traces
plain strings
unstructured objects
Prisma error objects
Zod error objects directly
Supabase raw error objects directly
```

---

# 6. Required Status Code Tests

Protected API routes must test at minimum:

| Situation | Expected Status | Expected Error Code |
|---|---:|---|
| No session | `401` | `UNAUTHENTICATED` |
| Authenticated but wrong organization | `404` | `ORG_NOT_FOUND` or safe equivalent |
| Module disabled | `404` | `MODULE_NOT_FOUND` |
| Authenticated but lacks permission | `403` | `FORBIDDEN` |
| Invalid route parameter | `400` | `VALIDATION_ERROR` |
| Invalid query string | `400` | `VALIDATION_ERROR` |
| Invalid body | `400` | `VALIDATION_ERROR` |
| Client-supplied `orgId` | `400` | `TENANT_ID_NOT_ALLOWED` |
| Record not found | `404` | `NOT_FOUND` |
| Conflict / duplicate | `409` | `CONFLICT` |
| Success create | `201` | none |
| Success read/update/delete | `200` | none |

Exact error codes may evolve, but the response must remain structured and testable.

# 7. Required Test Data

Every tenant-sensitive API test suite must include at least two organizations.

Minimum fixture set:

```txt
Org A
  Admin A
  Staff A with permission
  Staff A without permission
  Enabled module A
  Records belonging to Org A

Org B
  Admin B
  Staff B
  Enabled module B
  Records belonging to Org B
```

Do not write tenant-sensitive API tests with only one organization.

Single-org tests cannot prove tenant isolation.

---

# 8. Authentication Tests

Every protected API route must test unauthenticated access.

Example expectation:

```txt
Given no valid session
When calling a protected API
Then response status is 401
And response is JSON
And response body is { data: null, error: { code: 'UNAUTHENTICATED', ... } }
And response is not a redirect
And response is not HTML
```

Required assertions:

```ts
expect(response.status).toBe(401)
expect(response.headers.get('content-type')).toContain('application/json')
expect(body.data).toBeNull()
expect(body.error.code).toBe('UNAUTHENTICATED')
```

Forbidden API auth behavior:

```txt
307 redirect to /login
302 redirect to /login
HTML login page body
Next.js redirect exception leaking to tests
silent fallback to anonymous behavior
```

---

# 9. Tenant Isolation Tests

Every tenant-scoped API route must test wrong-organization access.

Example:

```txt
Given User A belongs to Org A
And Product B belongs to Org B
When User A calls /api/orgs/org-b/objects/products/product-b
Then the API returns safe 404
And does not reveal whether Org B or Product B exists
```

Tenant tests must cover:

```txt
wrong org slug
right org slug but wrong record ID
cross-tenant read attempt
cross-tenant update attempt
cross-tenant delete attempt
cross-tenant list attempt
client-supplied orgId attempt
```

Tenant isolation is not proven unless both reads and writes are tested.

---

# 10. Client-Supplied orgId Tests

All tenant-scoped APIs must reject client-supplied `orgId`.

This includes:

```txt
request body orgId
query string orgId
nested object orgId
filter orgId
metadata orgId
import row orgId
future AI/tool input orgId
```

Bad input example:

```json
{
  "name": "Test Product",
  "orgId": "org_b"
}
```

Expected response:

```json
{
  "data": null,
  "error": {
    "code": "TENANT_ID_NOT_ALLOWED",
    "message": "Tenant identity is resolved by the server. Do not submit orgId."
  }
}
```

Recommended test:

```ts
it('rejects client-supplied orgId', async () => {
  const response = await apiAs(staffA).post('/api/orgs/org-a/objects/products', {
    name: 'Test Product',
    code: 'TEST-001',
    orgId: orgB.id,
  })

  expect(response.status).toBe(400)
  expect(response.body.error.code).toBe('TENANT_ID_NOT_ALLOWED')
})
```

Important: do not merely strip or ignore `orgId` silently. Reject it so bad callers and bad generated forms are caught early.

# 11. Permission Tests

Every protected API mutation must test permission denial.

Example:

```txt
Given Staff A is authenticated
And Staff A belongs to Org A
And Inventory is enabled for Org A
But Staff A does not have inventory.stock_adjustment.create
When Staff A calls POST /api/orgs/org-a/inventory/stock-adjustments
Then response status is 403
And no record is created
And no event is emitted
```

Permission tests must include:

```txt
user with exact permission succeeds
user without permission fails
admin wildcard succeeds inside own org
admin wildcard fails outside own org
read permission does not allow export
create permission does not allow import
module enablement does not grant permission
permission does not bypass module enablement
```

---

# 12. Module Enablement Tests

Module APIs must test disabled-module behavior.

Example:

```txt
Given Inventory module is disabled for Org A
And User A has inventory permissions
When User A calls /api/orgs/org-a/inventory/products
Then response status is 404
And error code is MODULE_NOT_FOUND
```

This matters because module enablement and permissions are separate gates.

```txt
Module enabled + no permission = 403
Module disabled + permission exists = 404
Wrong organization = safe 404
```

---

# 13. Validation Tests

Every API route must test validation failure for:

```txt
invalid route params
invalid query params
invalid request body
missing required fields
wrong field types
unknown fields
client-supplied orgId
empty strings where prohibited
invalid enum values
invalid date formats
invalid relation IDs
```

Request body schemas should use `z.strictObject()` by default.

Unknown keys must be rejected.

Example:

```ts
it('rejects unknown request body keys', async () => {
  const response = await apiAs(staffA).post('/api/orgs/org-a/objects/products', {
    code: 'P-001',
    name: 'Product',
    randomField: 'bad',
  })

  expect(response.status).toBe(400)
  expect(response.body.error.code).toBe('VALIDATION_ERROR')
})
```

---

# 14. Relation Validation Tests

If an API accepts relation IDs, it must test that related records belong to the same organization.

Example:

```txt
POST /api/orgs/org-a/objects/products
body.categoryId = category from Org B
```

Expected:

```txt
400 VALIDATION_ERROR
or 404 NOT_FOUND
```

It must not create a cross-tenant relation.

Required relation tests:

```txt
valid relation in same org succeeds
relation from another org fails
soft-deleted relation fails
missing relation fails if required
inactive relation behavior is explicit
```

---

# 15. Soft Delete API Tests

APIs for soft-deletable records must test:

```txt
delete sets deletedAt/deletedBy
normal list excludes deleted records
normal detail endpoint hides deleted records
normal update cannot update deleted records
restore endpoint requires explicit restore permission
hard delete is not exposed through normal APIs
```

Expected behavior for deleted records:

```txt
Normal read after delete → 404 NOT_FOUND
Normal list after delete → record absent
Admin restore path → explicit route + explicit permission
```

---

# 16. Event Emission Tests

Mutation APIs indirectly cause service mutations. Tests should prove event behavior at the service or integration level.

At the API level, when practical, test:

```txt
successful create emits created event
successful update emits updated event
successful delete emits deleted event
failed validation emits no event
failed permission check emits no event
failed tenant check emits no event
```

Event payload tests must ensure payloads do not include:

```txt
orgId
full Prisma records
secrets
sensitive fields
large nested objects
```

---

# 17. No Redirect / No HTML Tests

Every protected API suite must include a test that proves API auth does not redirect.

Bad behavior to catch:

```txt
307 Temporary Redirect
302 Found
Location: /login
text/html content-type
HTML login page response
```

Recommended assertions:

```ts
expect(response.status).toBe(401)
expect(response.headers.get('location')).toBeNull()
expect(response.headers.get('content-type')).toContain('application/json')
expect(await response.text()).not.toContain('<html')
```

If the test client parses JSON, still include a lower-level test somewhere to ensure unauthenticated APIs are never returning HTML.

---

# 18. Current User API Tests

The current user endpoint must be:

```txt
GET /api/kernel/auth/me
```

It must not be:

```txt
GET /api/kernel/users/[id]
```

Reason: user identity must come from the session, not from a client-supplied ID.

Required tests:

```txt
unauthenticated → 401 JSON
authenticated → returns current platform user
does not accept arbitrary userId
includes org context needed for redirect
excludes sensitive internal fields
returns inactive/suspended status clearly if needed
```

Forbidden pattern:

```txt
/api/kernel/users/[id] used by login redirect
```

If a user-admin endpoint exists later, it must be clearly separate and permission-protected.

---

# 19. Registration API Tests

Registration is a special Kernel API and must be tested separately.

Required tests:

```txt
valid registration creates Supabase auth user + Organization + User + Subscription + Admin role
invalid input returns 400 JSON
duplicate email returns safe error
Prisma failure rolls back Supabase auth user
Supabase failure does not create Prisma rows
first org user becomes Admin
Admin role receives proper wildcard permission
no orphaned auth user remains after Prisma failure
no orphaned Prisma user remains after auth failure
```

Registration must be server-owned.

Forbidden pattern:

```txt
client calls supabase.auth.signUp() directly
then another mechanism tries to create Prisma user later
```

# 21. Recommended API Test Helper

Create a test helper to reduce repeated setup.

Possible future helper:

```ts
type ApiTestUser = {
  id: string
  orgId: string
  email: string
  role: 'admin' | 'staff' | 'no-permission'
}

type ApiTestClient = {
  get(path: string): Promise<ApiTestResponse>
  post(path: string, body?: unknown): Promise<ApiTestResponse>
  patch(path: string, body?: unknown): Promise<ApiTestResponse>
  delete(path: string): Promise<ApiTestResponse>
}

function apiAs(user: ApiTestUser): ApiTestClient
function apiUnauthenticated(): ApiTestClient
```

The helper must not bypass auth/permission logic in a way that makes security tests meaningless.

Allowed:

```txt
mocking Supabase session lookup to return a test user
using test database fixtures
calling actual route handlers
asserting actual response shape
```

Forbidden:

```txt
calling service methods directly and pretending it is an API test
mocking permission checks to always return true
mocking tenant context resolver to skip membership validation
mocking validation away
```

# 28. Mocking Rules

API tests may mock external services when necessary, but must not mock away the platform boundary being tested.

Allowed mocks:

```txt
Supabase Auth session return
email provider
SMS provider
file storage provider
AI provider
clock/time
random ID generator when needed
```

Dangerous mocks:

```txt
permission checker always returns true
tenant context resolver skips membership
service method mocked so database write is not tested
validation mocked away
event emission mocked away when testing event contracts
```

Rule:

```txt
Mock external systems.
Do not mock away OneDayOS security behavior.
```

# 29. API Tests vs Service Tests

API tests and service tests are different.

API tests prove:

```txt
HTTP method behavior
route parameter validation
query/body validation
auth behavior
JSON response shape
status code mapping
context creation
permission enforcement before service call
no redirects / no HTML
```

Service tests prove:

```txt
business rules
database writes
tenant scoping
permission enforcement inside service
soft delete
event emission
transactions
relation integrity
```

Both are required.

Do not replace API tests with service tests.

Do not replace service tests with API tests.

# 36. Anti-Patterns

## 36.1 Auth-only API

Bad:

```ts
await sdk.auth.requireApiAuth(req)
return service.create(input)
```

Why bad:

```txt
Authenticated does not mean authorized.
```

Good:

```ts
const ctx = await sdk.auth.requireApiModuleContext(req, orgSlug, 'inventory')
await sdk.permissions.require(ctx, {
  module: 'inventory',
  resource: 'stock_adjustment',
  action: 'create',
})
return InventoryService.createStockAdjustment(ctx, input)
```

## 36.2 Client-supplied tenant identity

Bad:

```ts
const orgId = body.orgId
```

Good:

```ts
const ctx = await sdk.auth.requireApiOrgContext(req, orgSlug)
const orgId = ctx.org.id
```

## 36.3 Redirecting API auth

Bad:

```ts
await requireAuth() // redirects to /login
```

Good:

```ts
const ctx = await sdk.auth.requireApiOrgContext(req, orgSlug)
```

## 36.4 Raw Prisma inside module API

Bad:

```ts
import { prisma } from '@/kernel/db/client'
```

Good:

```ts
const result = await InventoryService.create(ctx, input)
```

## 36.5 Testing only the happy path

Bad:

```ts
it('creates product', async () => {
  const response = await apiAs(adminA).post('/api/orgs/org-a/objects/products', body)
  expect(response.status).toBe(201)
})
```

Better:

```txt
also test unauthenticated, wrong org, no permission, invalid input, client-supplied orgId, duplicate code, relation from other org, no event on failure
```

# 37. Practical Testing Priority

For the restarted foundation build, prioritize API tests in this order:

```txt
1. /api/kernel/auth/register
2. /api/kernel/auth/me
3. first tenant-scoped Business Object API
4. first module API generated by Module Generator
5. first delete/soft-delete API
6. first restore API if restore exists
7. first settings API
```

The first few API routes become the pattern Claude will copy. They must be excellent.

---

# 38. Relationship to One-Day Delivery

Strong API tests may feel slower at first.

But they make future module delivery faster because Claude receives a known pattern:

```txt
same route shape
same context helper
same permission helper
same validation style
same response shape
same denial tests
same architecture checks
```

This prevents every new module from becoming a new security design session.

The goal is:

```txt
more rules now
less thinking later
faster safe modules later
```

---

# 39. Final Rule

```txt
API tests are where OneDayOS proves it is a platform, not a demo.
```

If API tests are weak, the platform will eventually leak data, bypass permissions, or become unsafe to update across many clients.

If API tests are strong, OneDayOS can update the shared base platform confidently while protecting every client organization.
